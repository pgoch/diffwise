# How it works

This page describes version 0.8. Diffwise compares two HTML documents in five steps, and then builds the views of the comparison: two columns or a single one, with hidden lines and blocks of changes. Plain text takes a shorter way to the same views; see [Plain text](#plain-text).

## 1. Clean and parse

Each version is cleaned with [DOMPurify](https://github.com/cure53/DOMPurify) and then parsed by the browser's `DOMParser`, which builds an inert document: no script runs and no image loads. This makes HTML from users or other systems safe to compare.

- **Removed:** scripts, event handlers such as `onclick`, `javascript:` links, `<style>` elements, and attributes that take focus or open popovers. Forms and dialogs are removed, but their content stays. Comments and hidden elements are left out, and so are attributes that start with `data-diffwise-`, so the content cannot pose as details of a change.
- **Kept**, so the content looks as it did in its editor: classes, inline styles that change only the look (such as color, font, alignment, spacing and borders, but no positioning and no `url()`), and checkboxes, which become read-only.
- **Links** that open a new tab get `rel="noopener noreferrer"`.
- **Ids** get a prefix of their own in each diff and each version, and in-page links follow them. Footnotes work within each version, and the ids never clash with the ones of your app.

## 2. Read the text and its format

Diffwise compares the text a reader sees, not the markup. A run of whitespace, including non-breaking spaces, counts as one space, except in `<pre>` and `<textarea>`. Blocks, images and line breaks separate words, and an image is one character of the text, so it is compared like a word. With `ignoreWhitespace`, all whitespace is ignored, and with `ignoreCase`, letter case.

Each piece of text also keeps its format: its formatting and the address of the link around it. Formatting is what the HTML says, not how a tag looks by default, since Diffwise cannot know how your app styles a heading or a class. So `<h2><b>Pricing</b></h2>` and `<h2>Pricing</h2>` differ in bold.

- **Formatting** comes from tags (bold, italic, underline, strikethrough, superscript, subscript, code, `<mark>` and `<small>`), from the heading level, and from the `style` attribute: text and background color, font, font size, weight, italic, underline and strikethrough, letter case, and the alignment of a block. The old `<font color face size>`, `align` and `<center>`, still found in emails, count too. Spacing, borders and dimensions do not, and neither do `class`, `title`, `datetime` or `id`.
- **The same look written another way is no change:** `<b>` and `<strong>`, `<i>` and `<em>`, or a color written as `#c0392b` and as `rgb(192, 57, 43)`. As in CSS, the nearest element decides the weight, the italic and the letter case, so `<b style="font-weight: normal">`, which Google Docs puts around pasted text, is not bold. Underline and strikethrough add up. A transparent background is no background.
- **Links** are compared by their address (`href`) as written. `target`, `rel` and `title` do not count. In-page links, such as footnotes, are compared without the prefix of their version.
- **Images** are compared by their file (`src`), their size and their alternative text. The size comes from `style`, or else from the `width` and `height` attributes, as in CSS, so `width="480"` and `style="width: 480px"` are the same. In the alternative text, single spaces count, as a screen reader reads it, and `ignoreCase` and `ignoreWhitespace` apply; a missing `alt` and an empty one differ. `srcset`, `class` and `title` do not count. Changes of other elements without text inside a line, such as `<svg>`, `<video>` or form fields, are not detected; the checkbox of a list item is the exception.
- **List markers** are read as the browser shows them. The style comes from `list-style-type` in `style`, or from `type`, of the item, the elements around it and the list, inherited as in CSS. The style, not the tag, says whether a list is bulleted or numbered: a `<ul>` with `list-style-type: decimal` shows numbers, so it is a numbered list. A list with the style `none` shows no markers, so its items, like paragraphs, have no marker to compare. Numbers are counted as the HTML standard counts them, with `start`, `value` and `reversed`, and the level says how deep an item is nested.
- **Checkboxes** count at the start of a list item, also inside a `<label>`, as in the task lists of GitHub, Notion or Markdown editors. A checkbox elsewhere, such as in a paragraph or a table cell, is not compared.

## 3. Split into lines

HTML has no real lines, so Diffwise uses blocks instead. A paragraph or a heading is one line, also inside a quote or a `<div>`, which are split into the blocks they hold.

- **Lists.** Each item of a list is a line, also in a nested list. In a definition list, each term and each description is a line. An item that holds blocks, such as a nested list or several paragraphs, is split further, and its marker stands at its first line. Each line holds copies of the lists around its item, and the copy of the item gets its number in `value`, so the item keeps its indentation and its number. An empty item is a line too, as its marker shows. `<li><p>Text</p></li>`, as Google Docs and many editors write it, is the same item as `<li>Text</li>`.
- **Tables.** The caption and each row of a table are lines, in the order a browser shows them: the caption, the head, the body and the foot, even when the foot comes first in the HTML. HTML put together from pieces can give a table more than one caption; each of them is a line above the rows, as a browser shows them. A table in a `<figure>`, as CKEditor writes it, is split too, and the caption of the figure is a line. A row of empty cells is a line, as its cells show, but a row without cells is not. A list or a table inside a cell stays part of its row.
- **One line each:** a code block, a `<details>` element and a figure with an image.

A line a reader would not see, such as an empty paragraph, is left out. The `id` of a list or a table stays in its first line only, so a link to it leads to its start. The lines of each version are numbered from 1.

## 4. Compare

- **Lines.** The lines of both versions are matched with the Myers algorithm, the one git uses by default. Two lines are equal when they have the same structure, text, formatting, links and images. A heading counts as a paragraph here, as its level is formatting, so a heading that becomes a paragraph is a changed line. The formatting of whitespace does not count, such as bold that also covers the space after a word. A list item is compared like a paragraph, without its marker, which is compared once the lines are matched. A table row equals another only with the same cells: the same text in the same columns, so text moved into the empty cell next to it is a change. Then, as in git, each group of removed or added lines slides over the equal lines around it until it meets the changes of the other version, so the old and the new version of a passage stand together, and an empty line never splits a changed line from its old version. A group that meets no changes ends as low as it can.
- **Changed lines.** Where the versions differ, a removed and an added line are paired as one changed line when they share at least half of their words. An image counts as two words: one that all images share and one for its file, so a paragraph whose image was replaced stays one changed line. Of the possible pairings, the one with the highest total similarity wins, and the order of both versions stays. The other lines are removed or added. A moved paragraph shows as a removal and an addition.
- **Words.** In a changed line, the text is compared word by word, again with the Myers algorithm. Words come from the browser's `Intl.Segmenter`, so languages written without spaces, such as Chinese and Japanese, are compared correctly. Each punctuation mark is compared on its own, and images are compared with the words, by their file.
- **Formatting and links.** In a changed line, the words that stayed are compared by their format. Each change gets a description: the styles before and after, a changed value such as a color, a heading level, or the old and the new address of a link. Neighboring words with the same change are one change. New text is a change of the text, so its formatting gets no description of its own.
- **Images.** An image removed and an image added between the same unchanged words are one changed image, described by what changed: its file, its size or its alternative text. An image without a pair is added or removed, like a word.
- **List markers.** In each pair of matched lines, also an unchanged one, the markers are compared: the list type, bulleted or numbered; the style, such as numbers → lowercase letters; the level; and the number. A paragraph that became a list item, or the other way around, is another list type. Another list type or level brings its own style, such as the circles of a nested list, so only the type or the level counts then. A pair that differs only in its markers becomes a changed line.
- **Item numbers.** Every number that differs between the two versions counts, whatever its cause: an item added or removed before it, also when an editor wrote the new numbers into `value`, a list that starts at another number, or an item with another number of its own. Another number reads as changed text, so its markers are marked like changed words, with no icon and no tooltip.
- **Checkboxes.** A checkbox of a list item that was checked or cleared makes the line changed. A checkbox in only one of the two lines does not count.
- **Table columns.** Before the rows are compared, the columns of the old and the new table are matched, once for the whole table. Two columns score a point for each pair of matched rows in which both hold a cell with the same text; empty cells and cells across several columns do not count. Of the matchings that keep the order of the columns, the one with the highest total score wins. Columns left between two matched ones are paired by position when both tables have as many of them, such as a column in which every value changed; otherwise they are removed and added. As the columns are matched for the whole table, an added column is the same column in every row, even where values such as "Unlimited" repeat.
- **Cells.** In a changed row, each cell is compared word by word with the cell of its column in the other version, so a change never runs from one cell into the next: text moved to another cell is removed from one and added to the other. A cell of an added or a removed column is marked whole, in every row, and so is each cell of an added or a removed row. Cells merged into one, or one cell split into several, are compared as a group. Formatting, links and images in cells are compared as in paragraphs.

`ignoreFormatting` leaves out formatting, heading levels and the look of list markers: the list type, the style and the level. Item numbers still count, as readers cite them. `ignoreLinkChanges` leaves out links added, removed or pointing elsewhere. Changes of images and checkboxes always count.

## 5. Mark and display

- Removed words are wrapped in `<del>` and added words in `<ins>`, inside the formatting, so a bold word or a link keeps its look. Text with changed formatting or a changed link gets the same markers, in both versions. Every line that shows a change is cleaned again after marking, and so is every line of a table, which also gets the columns of its table. An unchanged line outside tables is a part of the version cleaned before the comparison, so it is not cleaned again.
- A changed image gets a frame instead of a background, and the frame follows the marking style. An added or a removed image is framed only in its version.
- A changed list marker is drawn by Diffwise, as the marker of a browser (`::marker`) takes no background or frame. It is an empty `<del>` or `<ins>` at the start of the item, in place of the browser's marker, with the same text, such as "6." or a bullet, in the font of the item. It is marked like changed words, in each version that has a marker. Diffwise draws numbers, also with a leading zero, Latin and Greek letters, Roman numerals, and dot, circle and square bullets. A marker in a rarer style, such as Armenian numbering, stays the browser's and is not marked; the line still shows as changed. A merged line of the single column shows the old marker before the new one. The text of a drawn marker comes from CSS, so copied text leaves it out, as it leaves out the browser's marker.
- A checked or cleared checkbox gets a frame, like a changed image. A merged line of the single column shows the old checkbox before the new one.
- Each cell of an added or a removed row or column is marked whole, like changed words; in a changed cell, only the changed words are marked. A table row gets no background of a changed line, so the unchanged cells keep their colors, and the number with its bar shows that the row changed.
- A row with changes besides the text gets an icon in the column between the versions: formatting, link, image, or several changes with their number. Changed text and changed formatting in one line are two markers, and the icon is about the formatting only. Changes of list markers and checkboxes get no icon and no tooltip, as both versions show them.
- A tooltip on the icon and on the marked text says what changed, in the language of the interface: "italic → bold", "text color: ■ #c0392b → ■ #1e7d4f", "heading 3 → heading 2", "size: 480 × 270 → 640 × 360 px", or the old and the new address with the changed part highlighted. A file shows by its name, or by its whole address when both names are the same, and a long `data:` address is shortened.
- There is one tooltip for each diff, in the top layer of the page (the Popover API), so no `overflow` of your app cuts it. It stands under its icon or text, or above it when there is no room below. It shows on hover and on focus from the keyboard; the pointer can move onto it, and Escape or scrolling the page hides it.
- Each row of the view is a CSS grid: the number and the content of the earlier line, the column between the versions, and the number and the content of the later line. Matching lines stay level even when one of them is taller, and both versions scroll together. Opposite an added or a removed line stays an empty place.
- In each version, the rows of a table look like one table. Each row is a copy of the table with that row alone. The first row of each table also holds hidden copies of all rows of the table, already marked, which give it the columns of the whole table, and the other rows get the widths of its columns, measured once, and again when the width of the diff changes. The caption holds the copies too, as the columns widen it like the table. A table of more than 30 rows copies fewer rows: for each column, and for each set of columns that one cell spans, the row with the longest text there and the row with the longest word, so its columns may differ by a few pixels. A row grows to the height of the row opposite, so the table has no holes; a table inside a quote or a list does not grow. A table wider than its column scrolls as one, with the scrollbar under its last row. That row is the one stop of the table for `Tab`, so the keyboard can scroll it, and screen readers hear it as "Wide table, scroll sideways".
- Tables get a look of their own: a frame with rounded corners, lines between the columns, and a tinted background in header rows, which are the rows of `<thead>` and rows of `<th>` cells alone. Styles that the document gives its cells win over it. The caption stands above the table, as wide as the table. A cell across several rows (`rowspan`) shows its content in its first row; in the rows below, its place stays empty, with no line above it. A screen reader reads the rows as lines of the diff, cell by cell, and not as tables of one row each; it does not hear which header belongs to a cell.
- For screen readers, a removed, an added or a changed line starts with a description that does not show on the screen, such as "Changed line 2, before", in place of its number, which they skip. Side by side, they skip the old copy of an unchanged line, so they read it once, with its headings and links; `Tab` skips it too, and a click on its links still works. See [Accessibility](accessibility.md).
- **Drawing in parts.** After each comparison, the diff draws about two screens of rows at once, and then twice as many in each next moment, until every row shows, so a large document shows its first rows soon and the page answers clicks and scrolling in the meantime. While it draws, the find of the browser (`Ctrl+F`) does not see the rows still to come, and screen readers hear that the diff is busy (`aria-busy`). Stepping to a change, following a link inside the diff and printing draw the rest first.
- **Large documents.** From `largeDocumentLines` lines of the longer version, 20 000 by default, the diff compares the versions as usual, so the toolbar shows the numbers of changes at once, but draws no rows until the user asks for them with a button; then the rows draw in parts. Merged lines wait for the rows too. See [Configuration](configuration.md#lines).
- **Pages with many diffs.** The diffs of a page compare their versions and draw their first rows one by one, each in a moment of its own, the diff nearest the window first, so the first diff shows soon and the page answers clicks and scrolling in the meantime. A diff that waits for its turn stays empty, and screen readers hear that it is busy. A diff alone on a page starts at once. A page with very many diffs can also create each diff only when it comes into view, with Angular's `@defer`; the find of the browser then does not see the diffs not created yet:

  ```html
  @for (pair of pairs; track pair.id) {
    @defer (on viewport) {
      <diffwise-html [oldHtml]="pair.old" [newHtml]="pair.new" />
    } @placeholder {
      <div style="min-height: 400px"></div>
    }
  }
  ```

- The content of a line stays inside its cell, even an element that a class of your app gives a fixed position.
- Colors and sizes come from CSS variables, and the options add modifier classes to the component, so you can adjust the look in your CSS; see [Styling with CSS](configuration.md#styling-with-css).

## Plain text

The text diff, `<diffwise-text>`, compares plain text line by line with the same steps of comparison, and shows it in the same views.

- **Lines.** Each line of the text is a line of the diff, numbered from 1, empty lines too. `\n`, `\r\n` and `\r` end a line alike, so the same text saved on Windows and on Linux has no changes. A line end at the end of the text adds no empty line, and an empty text has no lines.
- **No HTML.** The text never becomes HTML: `<b>`, `&amp;` or `<script>` in the text show as these characters, and the only elements in a line are the markers of changes. The text needs no cleaning, so the text diff does not use DOMPurify.
- **Comparison.** Lines are matched and changed lines are paired as in HTML documents; see [Compare](#4-compare). Words come from `Intl.Segmenter` too, so text without spaces, such as Chinese, is compared correctly. `ignoreWhitespace` and `ignoreCase` work as in documents; with `ignoreWhitespace`, a line of spaces equals an empty line.
- **Whitespace.** Unlike in HTML documents, spaces and tabs count as written: two spaces differ from one, and a tab from spaces. Whitespace that changed alone is marked on its own, such as a changed indentation, a tab that became spaces, or spaces added at the end of a line. At the start and at the end of a line, changed whitespace stays in the marker also next to a changed word; between words, a marker starts and ends with a word.
- **Signs of whitespace.** Inside a marker, each space shows `·` and each tab `→`, such as `or·plain·text` for three added words, so a changed indentation or a space at the end of a line is visible. CSS draws the signs over the spaces, so copied text keeps plain spaces and tabs, and screen readers skip the signs. Other whitespace, such as a non-breaking space, has no sign. With `showAllWhitespace`, every space and tab shows its sign, lighter outside the markers; the lines then get the elements of the signs, so the versions are compared again.
- **Blank lines.** With `ignoreBlankLines`, a blank line, empty or of spaces and tabs alone, takes part in the comparison as an empty line, so spaces in place of an empty line are no change. A blank line added or removed is an unchanged line of its version alone: it has no colors of a change, but the empty place opposite stays, as for an added or a removed line, so the versions keep their lines in step. The numbers of changes and the navigation leave it out, and it hides with the unchanged lines. As in git, a blank line between two changed lines can still pair with them as they slide.
- **Display.** The lines keep the spaces, tabs and indentation of the text, and long lines wrap. A font of fixed width keeps indentation and columns in line; the user can switch to the font of the diff in the view settings.
- **Long lines.** With `wrapLines: false`, each line stays in one row of text, and the lines of both versions scroll sideways together, so the same columns of text stand opposite each other. Each line reaches out to the left by how far the lines are scrolled and shows only what is in its column, so a tab keeps its width. A scrollbar stands under each version at the bottom of the diff, and stays at the bottom of the window while the diff is in view, as the toolbar stays at its top; the single column has one. The scrollbars take their length from the texts of the five longest lines, in the font of the lines. The wheel with `Shift` or a touchpad over a line scrolls the lines too, and up and down movement stays with the page. While a line is wider than its column, the scrollbar of the new version is a stop of `Tab`, where the arrow keys scroll, and screen readers hear "Long lines, scroll sideways".
- **Changes besides the text.** Plain text has no formatting, links or images, so the text diff has no icons of changes and no tooltips.

## Views of the comparison

The single column, the hidden lines and the navigation work on the rows of the comparison, the same rows that the two columns show, in the same order. Switching the layout therefore keeps the hidden lines the user has shown and the block the navigation has stepped to.

- **Merged lines.** For the single column, each changed pair of lines becomes one line. It starts from the new line with its added words marked, and puts each removed part of the old line where it stood in the text: removed text that added text replaced stands right before it, 1px apart, so both markers show. The space between them is hidden, but screen readers read it and copied text keeps it. A removed part keeps its own formatting, such as bold or a link, and its `<del>` marker. Changes of formatting and links stay marked, with their icons and tooltips. A changed image shows as the old image, an arrow and the new image; a changed list marker or checkbox shows its old version before the new one. A pair that does not merge into valid HTML stays two lines, the old above the new. Like every line that shows a change, a merged line is cleaned again after marking.
- **Merged table rows.** A changed table row merges into one row with the columns of both versions. An added or a removed column stays in the table, marked whole, and the cell of a row whose version has no such column is an empty place. The words in each cell merge as in a paragraph. The tables of both versions are one table in the single column.
- **The single column.** An unchanged line shows once, in its new version, under the numbers of both versions. A changed pair shows its merged line, or, with `inlineDiffStyle: 'stacked'`, the old line above the new one. With `'strikethrough'`, removed text and whole removed lines are struck through with a thin line.
- **When merged lines are made.** The comparison keeps what merging needs, so merging does not compare the versions again: it merges the changed pairs and the tables, and cleans only the merged lines. A diff that shows two columns does not wait for it. After each comparison, once every row is drawn, it merges the lines while the browser is idle (`requestIdleCallback`), so the first switch to the single column is as fast as the later ones. A diff that can never show merged lines, because your app fixes the layout or the stacked look and the user cannot change it, merges nothing.
- **Hidden lines.** With `hideUnchangedLines`, each run of unchanged lines farther than `contextLines` from every changed line is hidden behind a bar with its number of lines; a run of a single line stays shown. Changed, added and removed lines always show, so the navigation never needs to show hidden lines. Hidden lines are not rendered, and a click on the bar renders them.
- **Blocks of changes.** Changed, added and removed lines with no unchanged line between them form a block, and the navigation steps from block to block. A passage rewritten across several lines is therefore one step. Both layouts have the same blocks.
- **Statistics.** The numbers count the rows of the comparison: added lines, removed lines, and changed pairs, each as one changed line, as the line numbers show them.
- **Layout.** `layout: 'auto'` measures the width of the component with a `ResizeObserver`, so a diff in a narrow panel shows a single column, and it switches as the width changes.

## Architecture

The diff engine is plain TypeScript with no dependency on Angular, and DOMPurify is its only dependency. It uses the DOM of the browser, so Diffwise does not support server-side rendering yet. The Angular package wraps the engine in the `DiffwiseHtml` and `DiffwiseText` components, `provideDiffwise()` and the `Diffwise` service. Both components share one view, with the same template and styles. Only the HTML diff uses DOMPurify, so an app that uses only the text diff does not bundle it. Angular puts the template and the styles into each component, so an app that uses both diffs bundles them twice, about 1.4 kB more after compression; the page gets the styles once. The engine describes changes with data, such as the styles before and after, and the component turns the data into the texts of the tooltips, so the engine knows no languages. The texts of each language besides English are a constant of their own, which the app gives to `provideDiffwiseLanguages()`, so the bundle of an app has only the languages it uses. The views of the comparison, such as the rows of the single column, the hidden lines and the blocks of changes, are plain functions of the engine too. This keeps the engine easy to test and leaves the door open for other frameworks later.
